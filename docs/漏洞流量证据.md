# 脆弱性に対する複数のトラフィック証拠

脆弱性詳細の「関連トラフィック」は、ページをまたぐ複数選択、用途・説明、並べ替え、関連解除に対応します。トラフィック画面から複数記録を選び、既存の1つの脆弱性にまとめて関連付けることもできます。継承したタスクの証拠は読み取り専用で、変更には元タスクを開く必要があります。

システム設定の「Agentによるトラフィック自動関連付け」は既定で無効です。`/api/settings`の`agent_traffic_binding`で取得・変更します。有効化するとリクエスト・応答の参照、ツール呼び出し、プロンプトによるトークン使用量が増え、次のAgentラウンドから反映します。無効時は自動関連付けの引数と追加ツールを隠し、指示も注入せず、実行済みセッションからの新たな自動関連付けも拒否します。手動関連付け、トラフィック取得、保存済み証拠の閲覧・出力は影響を受けません。

有効時の標準フローは「検出を保存 → レポートAgentを自動起動 → トラフィックを照合・関連付け → 最新の証拠バージョンでレポート保存」です。報告側は`evidence`に検証コマンド、主要出力、既存の実トラフィックIDと用途を残します。レポートAgentは脆弱性詳細と実行記録を踏まえ、`traffic_search` / `traffic_get`で照合し、`bind_finding_traffic`を呼び、最新`version`を読み取ってレポートを保存します。無効時は生トラフィック検索・取得ツールを追加せず、自動関連付けもしませんが、手動で紐づけたスナップショットを読み取り、レポートを作成できます。

既存の呼び出しとの互換性を保ち、`report_finding`の`traffic_refs` / `evidence_hint_id`で明示的に即時関連付けできます。関連付けは任意で、TCPなどの非HTTP脆弱性、未取得、該当記録なしの場合は参照を省略して報告・レポート作成ができます。コマンド出力やログなど検証可能な証拠を残し、未関連付けの理由を記すことを推奨します。必須フィールドは追加しません。送信IDはすべて有効で本文が完全である必要があります。1件でも失敗すれば今回の関連付け全体をロールバックし、報告と同時の明示的関連付けに失敗した場合は報告全体を戻します。同じスナップショットの重複追加は、件数を増やさず説明も上書きしません。

## Agent向けのIDとレポートバージョン

`report_finding`の新しい任意引数では、配列順が初期の証拠順です。

```json
{
  "traffic_refs": [
    {"traffic_id": "実トラフィックID", "role": "baseline", "note": "正常アカウントのリクエスト"},
    {"traffic_id": "別の実トラフィックID", "role": "proof", "note": "再現リクエスト"}
  ]
}
```

用途は`baseline`（正常対照）、`proof`（脆弱性の証明）、`verification`（追加検証）、`supporting`（補助証拠、既定）です。先に`traffic_search` / `traffic_get`で実記録を照合してください。ドメインと時刻は候補抽出専用で、タスクへの所属を推定しません。

プロンプトは[CyberStrikeAIの脆弱性報告ツール指針](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go)を参考にし、本プロジェクトの任意関連付け契約に合わせています。パケットがない理由の必須検証は追加しません。IDを推測せず、補完だけを目的に再探索しないでください。

応答の1行目は引き続き`finding recorded: <探索ノードID>`です。後続JSONには独立した脆弱性記録の`finding_id`、探索ノードの`finding_node_id`、関連付け概要が含まれます。

- `get_finding_traffic(finding_id)`は**独立した脆弱性記録ID**を使用し、順序付き一覧と`version`を返します。`binding_id`、`side=request|response`、`offset`、`length`で分割取得でき、1回最大8192バイトです。
- `update_finding_report`の`finding_id`は**引き続き探索ノードID**です。新しい`evidence_version`には実際に読んだバージョンを指定します。生成中に証拠が変わると旧版の保存は拒否され、再取得・再生成が必要です。
- バージョンを送らない旧呼び出しでは、既存のトラフィック証拠を反映したと表明しません。関連付け、説明、用途、順序が変わると、既存レポートは要更新と表示します。

自動関連付け有効時は、`add_hint` / `add_task_hint`の単一ヒントまたは`hints`配列の各要素に`traffic_refs`を保存できます。Plannerの代理報告は`evidence_hint_id`で当該タスクのヒント内参照を明示的に選び、継承ヒントは参照できません。ドメイン・時刻・閲覧履歴から関連付けを推定しません。送信失敗では部分的な脆弱性作成やレポートの早期起動は起こりません。

既存脆弱性の関連付け漏れは`bind_finding_traffic(finding_id, traffic_refs)`で補い、再登録は不要です。`list_findings` / `list_task_findings` / `node_detail` / `get_task_node_detail`は明確な`finding_id`と`finding_node_id`を返し、旧`id`は探索ノードの意味を維持します。

起動時は旧ツールschemaへ任意属性のみを追加し、元の標準トラフィックツールの割り当てをレポートAgentへ拡張します。追加関連付けツールも標準でレポートAgentに渡します。カスタムの割り当て一覧、プロンプト、説明、有効状態は保持します。指針は最終ツール構成後にまとめて追加します。報告担当は既存証拠を引き渡し、レポートAgentが照合・関連付け・執筆を担当します。タスクコンテキストのないプラットフォーム対話では直接報告せず、構造化ヒントでタスクAgentに渡します。タスク完了判定前に既存証拠を引き渡しますが、パケットがなければ待機を強制しません。失敗した`report_finding`はレポートAgentを起動しません。

## API

ベースパスは`/api/exploration/findings/{finding_id}/traffic`で、独立した脆弱性IDを使用します。既存認証を用い、`context_task`でタスクの可視性と継承時の読み取り専用を検証します。

| メソッド / 相対パス | リクエスト / 応答 |
| --- | --- |
| `GET` | 順序付き概要、証拠バージョン、レポート採用バージョン |
| `POST` | `{"traffic_refs":[...]}`を一括追加 |
| `PATCH /{binding_id}` | `{"version":1,"role":"proof","note":"説明"}` |
| `DELETE /{binding_id}` | `{"version":1}` |
| `PUT /order` | `{"version":1,"binding_ids":["2","1"]}`。完全な一覧が必要 |
| `GET /{binding_id}` | スナップショットメタ情報と上限付き本文プレビュー |
| `GET /{binding_id}/body` | `side`、`offset`、`length`。`download=1`で完全な元バイト列を取得 |

バージョン・並び順集合の競合、アーカイブ中の書き込みは`409`、継承データへの書き込みは`403`、存在しない・別脆弱性に属する関連付けは`404`です。トラフィック・添付ファイルの取得と検証の失敗は明示的なエラーを返します。

## 保存とマイグレーション

起動時の冪等なPostgreSQL移行で`traffic_evidence_snapshots`、`finding_traffic_bindings`、`findings.evidence_version` / `report_evidence_version`（既定0）を追加します。過去の文章から関連付けを推測しません。

スナップショットは元トラフィックID、取得時刻、URL、メソッド、状態、リクエスト・応答ヘッダー、本文長、SHA-256を保存します。本文はハッシュ別の`<data>/evidence/blobs/<先頭2文字>/<hash>.bin`に保存し、削除可能な`data/traffic`から独立しています。複数の脆弱性でスナップショット・本文を共有できます。スナップショットの内容更新APIはなく、検証不一致では読み取り・出力を失敗させます。

元トラフィックの書き込みロック下で、大本文blobや旧ディレクトリ記録を含む本文全体を取得します。先にファイルを永続化・検証し、単一PostgreSQLトランザクションで探索ノード、intent関係、脆弱性、スナップショット、関連付けを書き込み、コミット後にのみplannerへ通知します。失敗時に未参照ファイルが残る場合はありますが、業務記録は部分作成しません。

PostgreSQL advisory lock `7337741004`で証拠ファイルとSQL参照を調整します。タスク行ロックによりアーカイブ待ちになった後の証拠変更を禁止します。復元は本文配置からメタデータのコミットまで証拠ロックを保持します。脆弱性の削除では関連付けもカスケード削除します。

クリーンアップは毎時実行し、未参照かつ進行中操作に関係しない内容のみを、最低24時間経過後に回収します。通常のトラフィック削除は証拠ディレクトリに触れません。稼働データのバックアップではPostgreSQLと`data/evidence`を同時に保存してください。

## エクスポートとアーカイブ

Markdownは順序付き証拠一覧とバージョン、JSONはメタ情報、CSVは件数と関連付けIDを含みます。`md-zip`は脆弱性Markdownに加えて次を出力します。

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

Markdownは相対リンクで通信内容を参照します。ダウンロード送信前に添付コピー、ハッシュ検証、圧縮、ディスク同期、全ZIPエントリーのCRC読み取り検証を完了し、欠落・破損があれば全体を失敗させます。完全な添付は元のバイナリバイト列を保持します。

アーカイブv3は脆弱性の関連付けに基づいてスナップショットと本文を収集し、元トラフィックやドメインに依存しません。パッケージ検証後にのみ稼働データを削除し、共有証拠は保持します。復元は先に本文を検証・配置し、トランザクションでメタ情報と関連付けを復元します。失敗後の再試行が可能です。v1/v2も引き続き復元でき、欠ける新フィールドは明示的に0で補います。

## 検証と制限

テストパッケージごとに独立した新規PostgreSQLテストDBを用意し、`ARTEX_PG_DSN`で指定します。残存タスク・モデルフィクスチャによるバックグラウンド起動を避けます。関連パッケージの全テストを実行し、設定不足によるスキップがないことを確認します。

```sh
# 各パッケージの実行前に専用DBをARTEX_PG_DSNへ設定。明示した設定の失敗はエラーにする。
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

フロントエンドの検証は`npx tsc --noEmit`、変更ファイルのBiome、Webpackビルド、`NEXT_EXPORT=1`の静的エクスポートを含みます。稼働中の開発サービスを上書きしないよう独立キャッシュを使用します。

ローカルE2E検証では独立ポート、制御可能なHTTP / ドメインHTTPS対象、一時データディレクトリを使い、2つの関連付け入口、ページ間選択、並べ替え・説明、エラー表示、継承の読み取り専用、ダウンロード、元トラフィック削除後の出力・アーカイブ・稼働本文回収・復元・ハッシュ照合を確認しました。

初版はグローバルな証拠調整ロックを使用するため、大量の関連付け・出力や低速な添付ダウンロード中は他の証拠操作が待つ場合があります。記録や完全な本文がない場合、証拠を捏造できません。この機能は取得スイッチを変更せず、HTTPSでIPへ直接アクセスする際の証明書問題も扱いません。
